Tour

See what each RTL Buddy workflow produces before you set one up. Every command below ran unchanged against rtl-buddy-project-template, and every table and image is that run's actual output. The project is a multi-clock APB-mapped ALU accelerator built from small leaf IPs, so one design carries the whole tour.

To follow along:

git clone https://github.com/rtl-buddy/rtl-buddy-project-template
cd rtl-buddy-project-template
uv sync --locked
uv run rb tool-check          # which flows your machine can run right now

rb tool-check lists each external tool and marks every rb subcommand ready or blocked. Only Verilator is needed for the first three sections; Installation maps the rest.

Run one test​

A test is one named entry in a suite's tests.yaml. RTL Buddy resolves the model filelist, compiles, simulates, and grades the log.

Look at the waveform​

rb wave opens the test's trace in Surfer with the suite's saved signal layout, and streams signal values back into your editor over the hub. The same layout file drives headless capture, which is how this image was made:

cd verif/demo_tiny_alu
uv run rb wave basic

Stimulus, DUT outputs, and the scoreboard's mismatch counter sit in three named groups because tb_top.surfer says so; a new engineer opening the test sees the same thing you do. See Waveform Viewing.

Draw the hierarchy​

rb hier renders a model's instance tree from the RTL. The block-diagram form groups siblings and labels the nets between them:

cd design/demo_tiny_alu_subsys
uv run rb hier demo_tiny_alu_subsys_top
uv run rb hier demo_tiny_alu_subsys_top --format dot --block-diagram | dot -Tpng -o subsys.png

├── u_hs_cmd : ip_cdc_handshake
├── u_afifo : ip_async_fifo
├── u_sync_src : ip_cdc_sync

Parameter values on each block come from the elaborated design, not from a drawing. rb hier-query answers the same questions as JSON (see Ask the design questions below), and rb hub serves an interactive schematic of the same hierarchy in the browser. See Hierarchy Rendering.

Profile an interconnect​

rb axi-profile discovers AXI bundles from the RTL, binds a monitor into the simulation, and turns the trace into per-channel utilization, back-pressure, latency percentiles, and a per-transaction table.

cd verif/demo_axi_2x2
uv run rb test basic_traffic
uv run rb axi-profile run basic_traffic
wrote artefacts/axi/basic_traffic/axi-perf.json (4 bundles, 3210 cycles, clock=tb_axi_2x2.clk).

For the in0 bundle of the 2×2 crossbar, the write-data channel reports 55% back-pressure against 4.8% utilization, which is the deliberate stall the testbench injects. rb axi-profile notebook opens the same data in a packaged marimo notebook, and the hub overlays it on the schematic. See AXI Interconnect Profiling.

Browse it live in the hub​

rb hub is a small daemon that serves four browser panes over the artefacts the sections above produced, and keeps them, Surfer, and your editor pointed at the same thing. One client per pane; a click in any of them selects in the others.

uv run rb graph build
uv run rb hub start --serve-viewer --model demo_tiny_alu_subsys_top \
    --models-file design/demo_tiny_alu_subsys/models.yaml

Schematic (/sch). The hierarchy from rb hier, drawn by rtl-buddy-sch with a DUT or testbench root, an instance filter, and overlays. The coverage overlay below colours each block by line coverage from the latest run; only the ALU under u_compute has a coverage run behind it, so only it is green:

Knowledge graph (/gph). The 800-node graph from rb graph build, laid out by tier: spec, design, test config, synthesis config, formal config, CDC config, and cocotb. Clicking a node selects it in the schematic and opens its source in the editor:

Coverage (/cov). The same manifest rb cov summary reads, with per-test columns, per-file bars, and every cover point with its hit count. A click on a source line sets the coverage focus everywhere else:

Area and power (/phy). The physical model that rb synth and rb power wrote, ranked by cells and by instance power, with the run selector at the top switching between the four power runs:

Every pane is one self-contained HTML file served from the wheel, so the hub needs no network access and no build step. rb hub send scripts the same selections from a terminal, and rb mcp exposes the hub's state to an agent. See Hub.

Annotate your editor​

The Neovim plugin is the editor side of the hub. rb nvim-install clones rtl-buddy-nvim and wires it in with one command; the plugin composes with verible-verilog-ls rather than replacing it.

uv run rb nvim-install

Two annotations appear without any hub running. rb wave launches Neovim with the selected signal's value as virtual text at its declaration, and <leader>wa adds the signal under the cursor to the Surfer waveform:

Every module declaration carries its synthesized cell count and area, read from the same physical model the /phy pane shows, through one rb --machine phys summary call per project:

With the hub connected, a click on a schematic instance opens its file at the right line, :RtlBuddyShow pans the schematic and Surfer to the cursor, and :RtlBuddyToWave adds the symbol under the cursor to the waveform. Both captures above are the real Neovim screen grid, rendered through the UI protocol. See Install the nvim integration.
